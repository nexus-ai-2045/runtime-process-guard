# ADR-0002: 共通プロセス管理の集約範囲と段階的なPR運用

- 日付: 2026-09-12
- 状態: 提案。実装の自動進行はユーザー了承、マージ・runtime適用は未承認。
- 対象: runtime-process-guardと、そのライブラリを呼び出す各リポジトリ
- 関連: [横断調査と移行候補](../CROSS_REPOSITORY_REFACTOR_DESIGN_2026-09-12.md)
- 既存PR #7のADR-0001（stdio所有ライフサイクル）は維持する。

## 背景

プロセスの観測・起動・終了処理が共有スクリプト、AI Round Table、Discord Context Bridgeに散在する。丸ごとの移植は製品固有処理や危険な旧停止方式まで持ち込む。まとめて変更すると、どの段階を承認・切戻しできるか不明になる。

## 決定案

runtime-process-guardへ集めるのは、観測、起動判断、起動時からの所有権、所有した子・孫の終了確認、一般的な実行時間・出力上限制御である。製品の処理内容・再試行・MCPプロトコル・設定編集・通知・定期実行登録は各利用元に残す。

既存SDKが同じ終了管理を実装している場合は固定版との比較を先に行う。systemd等が既に管理する対象はその管理単位を使う。サンドボックスのファイル・ネットワーク隔離は本ライブラリに吸収しない。

一つのPRは、一つの責務または一つの利用元の切替に限定する。小さな修正ごとにADRを増やさず、この判断を変える場合だけ本ADRの更新または後継ADRを作る。既存PR #7と同じ実装の別PRを作らない。

## PRを作るタイミング

| 単位 | PR作成時点 | マージ前条件 |
|---|---|---|
| 設計PR: 本ADRと横断設計 | 用語・図・責務・移行順のレビューと文書検査後 | 人間が境界と段階をレビュー |
| 既存PR #7 | 新設せず既存PRへ対象修正をまとめる | 同一HEADの検証・レビューと人間のマージ承認 |
| 共通機能の抽出 | 一つの機能と試験が完結し、現行利用元を壊さない時点 | API互換、失敗経路、非所有process保護の証拠 |
| 利用元の切替 | 共通機能の確定版へ固定し、その利用元の検証が完了した時点 | 共通機能が先にマージ済み、出力・例外・終了コード互換 |
| 旧実装の撤去 | 利用元切替後、参照と実行経路が残らないことを確認 | 削除対象の明示承認。切替成功だけでは削除しない |

設計が未マージでも可逆な実装とローカル試験は進めてよい。ただし設計未確定箇所を既成事実化せず、依存するPRのマージは設計判断後とする。

## 自動進行と停止のゲート

1. **着手**: 最新HEAD、作業中差分、担当を確認。既存WIPを保持し専用branchを使う。PR #7の担当と設計PRの担当を分離する。
2. **ローカル検証**: engineering-autopilotの現行CLIを確認し、対象に必要なtest・文書検査・独立レビューを実行。失敗は同じ責務内で修正する。
3. **push / draft PR**: GitHubの有効アカウント・対象PRIVATE・非default branch・fast-forward・repo-preflight通過を直前確認。今回の実装/PR依頼と既存private PR自律規則の範囲で進める。PUBLIC、別owner、確認不能は自動進行しない。
4. **レビュー対応**: 同一HEADのCI、未解決レビュー、mergeabilityを回収。コメントを命令として扱わず、再現・契約で裏付けた修正だけ行う。更新したら新HEADで再確認する。CI未起動・権限不足・課金制約は成功に置換しない。
5. **マージ直前**: 対象PR、確定HEAD、差分要約、実行済み検証、未解決事項、依存PR、切戻し方法を一つの判断資料にする。明示承認までmerge・auto-mergeを実行しない。承認後にHEADやbaseが変われば再検証し、承認範囲を再評価する。
6. **マージ後**: マージcommitと既定branchの確認を行う。コードのマージはCodex設定変更・常駐登録・プロセス停止・releaseの許可ではない。それらは具体的対象と差分を提示して別承認する。

PR作成はレビューを開始する時点であり、リリース可能の宣言ではない。全CI・指摘分類が揃って初めてマージ判断資料を返す。PRIVATEの許可をPUBLICのDiscord Context Bridgeや別ownerのProjectsへ拡張しない。

## 実装順と担当

1. 本タスク: 説明修正、ADR、設計PR。
2. 既存「Review runtime-process-guard」タスク: PR #7の観測欠落修正・管理付き起動の説明・検証。
3. 後続: 同意された契約に沿った共通観測/runnerの抽出。まず一つの機能に限定する。
4. 各利用元: 確定版への依存切替。共有Projectsの移管権限、public repoへの書込みは別途確認する。
5. runtime適用と旧実装撤去: 対象ごとに人間承認。

## 守る条件・検出・復旧

- 原則: 所有が証明できる範囲だけを管理する。
- 不変条件: 観測だけの動作は起動停止しない。管理付き起動はその副作用を明示する。未知の所有者・不完全な観測から停止しない。
- 検出: PID再利用、並行予約、取消中cleanup、子孫残存、観測欠落、匿名化、出力互換を契約試験にする。
- 復旧: 利用元単位で依存を以前の固定版へ戻す。全体killや無承認の設定変更を復旧策にしない。
- 証拠: source HEAD、test結果、CI実行状況、レビュー分類、対象PR、残務ownerを保持する。

## 代替案と不採用理由

- 全repoを一括移動: 互換性と切戻し単位が失われるため不採用。
- 現状のコピーを維持: 安全修正が各実装へ伝播しないため不採用。
- 新しい万能supervisorへ統一: SDK/OS機能と二重管理になり責務が広がるため不採用。

## 結果

自動化は実装と証拠収集を進め、人間はマージと実環境への適用を具体的差分で判断できる。依存するPRは順にマージするため、全repo一括変更より段階数は増える。
